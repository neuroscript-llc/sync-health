This document sets out how the Sync. website will source, process and submit data once Bask Health is connected as the commerce and clinical backend. It answers three things: what Bask owns, how add to cart and checkout work against it, and what the frontend is responsible for once the backend is doing the heavy lifting. It closes with the eight decisions we need from you.

The model in one paragraph

The Sync. site is a headless build. Three systems are involved and each owns exactly one thing. Storyblok owns marketing content: copy, imagery and the composition of each page. Bask Health owns commerce and clinical data: the product catalogue, pricing, plans, orders, payments, patient records, prescriptions and pharmacy routing. The Next.js frontend owns presentation and nothing of record. It reads from both systems and writes to Bask through server side calls. It holds no database of its own and is never the source of truth for anything a customer is charged for.

What Bask owns

Confirmed from Bask's public documentation:

  • The product catalogue. The brand operator configures what is offered, covering over the counter medication, prescription medication and devices, inside the Bask dashboard.
  • Checkout and payment processing, including a PCI compliant vault for stored cards, subscriptions, billing plans, coupons, disputes and payout settings.
  • Prescription routing into a network of more than thirty pharmacies, including 503A and 503B compounding pharmacies.
  • A REST API with separate test and live keys, event webhooks, and JavaScript and React SDKs.
  • Both a hosted checkout and a fully custom checkout built on that API.
One point to settle on inventory

Bask is the single source of truth for catalogue and pricing, and the site should fetch both rather than duplicate them. Inventory is the exception. In compounded telehealth there is normally no retail stock counter, because the constraint is the pharmacy's ability to fill a prescription rather than units on a shelf, and Bask's documentation does not describe one. The design should therefore avoid stock messaging such as "in stock" or "only two left" unless Bask turns out to expose it.

How content is processed from the backend

Every page renders on the server, per request. There is no build step that bakes in prices and no cache that could serve a stale figure. For a product page:

  1. The visitor requests the page and Next.js begins rendering on the server.
  2. The server reads that page's marketing content from Storyblok: headings, body copy, imagery, section order.
  3. In parallel, the server calls the Bask API for the catalogue entry and its pricing, using an API key held only on the server.
  4. The two are merged. Storyblok supplies the words and pictures, Bask supplies the product identity, price and available plans.
  5. Finished HTML is returned. The Bask key never reaches the browser.

Three rules govern this:

  • Anything sensitive stays server side. Every Bask call carrying a key or patient information runs inside a server component or route handler, so no credential is shipped to the browser and no clinical data passes through client JavaScript where an analytics tag could observe it.
  • Price always comes from Bask. Prices render from the live API response rather than a CMS field, so a content edit cannot contradict what is actually charged.
  • The site degrades rather than fails. If Bask is unreachable, the page still renders its marketing content and the purchase action is disabled with a clear message.

Add to cart

Today the cart is entirely browser side. Adding a product writes a line item into browser storage, so the cart survives refreshes and navigation, recording the product, the selected plan and the quantity. No server is involved, because Bask is not yet connected.

Once Bask is connected the cart stays where it is, with one change: each line item references a Bask product and price identifier rather than a piece of CMS text. Nothing is created in Bask until the customer begins checkout, at which point the cart is posted to our own server route, revalidated against live Bask pricing, and turned into an order. If Bask turns out to expose a server side cart we will use it instead, which would also give us abandoned cart recovery.

The rule that holds either way

The amount charged is always the amount Bask returns at checkout, never the amount the browser submitted. The browser cart is a convenience for the customer, not a binding instruction to the payment system, and that is what prevents a tampered or simply stale cart from producing a wrong charge.

Checkout

Bask offers two checkout routes, and the choice determines whether the checkout already built to the Sync. design is used at all.

Checkout options compared
Option What it means Trade off
Hosted checkout The customer leaves the Sync. site and completes payment on a page hosted by Bask. Fastest to launch and the smallest compliance surface for us. The Sync. checkout design is not used, and the customer sees a branding and domain change at the most sensitive moment of the journey.
Custom checkout Recommended The checkout already built to the Sync. design is driven by Bask's API and SDK, with card entry handled by Bask hosted payment fields embedded in our page. Full control of the experience and no loss of the work already completed. Raw card numbers never reach Sync. servers, so PCI scope stays with Bask. More integration work and a longer test cycle.

Custom checkout is our recommendation. It preserves the design, keeps the customer on the Sync. domain, and matches the reassurance already written into the checkout copy, which tells the customer that card details are handled by Bask and that Sync. never sees the card number.

Checkout in this category is not retail checkout

This is the part most often missed when a telehealth build is scoped like a normal store. A purchase is not complete when payment succeeds. The full sequence is:

  1. The customer selects a product and a plan.
  2. The customer completes the intake questionnaire. This is clinical information, submitted to Bask and not retained by the frontend.
  3. The customer provides shipping and payment details and gives the consents shown in the design, including consent to a telehealth consultation.
  4. Bask creates the order and authorises payment.
  5. A licensed provider reviews the intake. This happens after checkout and is asynchronous.
  6. If approved, Bask issues the prescription and routes it to a pharmacy. If declined, Bask handles the cancellation or refund.
  7. Bask emits a webhook at each state change. Our server receives these, updates order status and triggers the appropriate customer messaging.
Design consequence

The confirmation page cannot say the order is on its way. It has to say the order is pending clinical review, and the customer needs somewhere to see the outcome afterwards. There is also no intake step anywhere in the current design. It sits between product selection and payment, and it will need designing and building.

What the frontend is for

Bask supplies infrastructure. It does not supply a website. The following are entirely the frontend's responsibility and none of them are solved by connecting an API.

The brand and the marketing site
Home, product pages, the journal, about, contact and the policy pages. None of this is commerce and none of it exists inside Bask. Bask's own storefront is a template product, so using it would mean discarding the Sync. design entirely.
Client editable content
Storyblok is what lets the client change copy, imagery and section order without a developer. Bask has no equivalent for marketing content.
Search visibility
URLs, page titles, metadata, structured data and page speed live in the frontend and directly affect acquisition cost. A hosted storefront gives away control of all of them.
The intake experience
Bask holds the questionnaire logic and the clinical record, but how that questionnaire looks, how many steps it takes and how many people finish it is a frontend problem. It is one of the highest leverage points in the whole funnel.
Consent, privacy and tracking control
The consent platform, the tag manager and the rules governing what is allowed to reach Meta and Google sit in the frontend. In a category where a URL can itself disclose a health condition, that is a compliance requirement rather than a preference.
Cart and checkout experience
Plan switching, quantity handling, upsells, the order summary, error states and the recovery paths when something goes wrong.

In short, Bask is the system of record and the regulated engine underneath. The frontend is the product the customer actually experiences, and it is where conversion, brand and compliance are won or lost.

Current state of the build

  • Every page renders on the server per request and reads its content from Storyblok, with a code level fallback if Storyblok is unreachable. This is live.
  • Product pages, price displays and plan selectors are built and fully content driven, currently sourced from Storyblok rather than Bask.
  • The cart is complete on the client side: add, change quantity, switch plan, remove, and a persistent subtotal that survives navigation.
  • The checkout page is built to the design, including consents and payment method selection, but it has no submit action and calls no payment or order API.
  • There is no Bask code and no Bask credentials in the project.

The commerce layer therefore exists as a complete interface waiting for the backend it will talk to. Connecting Bask means replacing local data sources with API calls and adding a submit path, not rebuilding the front of the site.

What we need in order to proceed

  1. A Bask account with dashboard and documentation access. The technical reference sits behind a Bask login. Until we can read the endpoint contracts, any estimate for this integration is a guess rather than a plan. This blocks everything else.
  2. Test and live API keys, plus a sandbox with data usable enough to run a full order through, including a simulated clinical approval and decline.
  3. A technical contact at Bask, so integration questions are answered once rather than discovered one at a time during the build.
  4. Access to the existing Shopify store and Klaviyo account, since both are live on the domain today and both affect the cutover.

Decisions we need from you

The technical specifics of this integration are ours to resolve. Endpoint contracts, how the cart resource works, rate limits and caching, tax and shipping calculation, discount validation, webhook semantics and idempotency will all be answered by Bask's API reference the moment we have access to it, and we will not be asking you about any of them.

The following eight are different. They are commercial, clinical or legal decisions that we cannot make on your behalf, and each one changes what gets built.

  1. 1Who owns the catalogue? Do the nine products already exist in Bask, or does someone need to create them there. Once live, when a product is added, repriced or withdrawn in Bask, who is responsible for keeping the matching Storyblok entry in step. Two systems each holding half of a product will drift unless one person owns the routine.
  2. 2Which products can be sold, to whom, and where? Telehealth is licensed state by state and compounded products are commonly restricted, so we need the list of what can be sold in which states. We also need to know whether any age or identity verification is required before purchase, and whether the offering is United States only. There is no eligibility check anywhere in the current design. A customer discovering after payment that they cannot be treated is the worst version of this, so it has to be handled on the product page or early in checkout.
  3. 3Can a customer buy more than one prescription product in a single order? The cart already supports several line items. If each prescription requires its own clinical review and therefore its own order, the cart either splits into multiple orders or should not offer multiple items at all. We also need to know whether a prescription item and an over the counter item can travel together, since one can ship immediately and the other cannot.
  4. 4How should the money work around clinical review? The checkout currently promises customers in writing that their card is authorised at purchase and charged only if a clinician approves. We need that confirmed as the intended commercial behaviour, along with what happens when a clinician declines: full refund, or a retained consultation fee. Whatever is decided has to match the refund policy page word for word.
  5. 5Who builds the intake questionnaire, and where does it sit? Either Bask hosts the questionnaire and we hand off to it, or Bask provides the questions and we build the experience inside the Sync. journey. The second is significantly more work and needs design before it needs code. We also need to know whether intake comes before or after payment, whether a live consultation is ever required rather than an asynchronous review, and what the genuine review turnaround is, since the site currently tells customers most reviews complete within one to two hours.
  6. 6Does Bask's patient portal cover customer accounts, or do we build them? Subscriptions are being sold from launch, which means customers need somewhere to sign in, see order status while a review is pending, view history, and pause, skip or cancel a plan and update a card. If Bask's portal handles all of that we link to it. If it does not, this is a substantial additional build that is not in the current design or estimate.
  7. 7What is the compliance position? Two parts. First, whether a business associate agreement is required and between which parties, because the site's own privacy policy already tells customers that infrastructure vendors are bound by them. Second, what is permitted to reach Google and Meta, given that a product level purchase event discloses a health condition and the product URLs currently contain compound names. We will build to whichever line is drawn, but the line is a legal call rather than an engineering one.
  8. 8What happens to the store that is live on the domain today? The domain currently runs a Shopify store with Klaviyo attached. We need to know whether it is being retired, whether there are existing customers, orders or active subscriptions that have to move, which existing URLs need redirecting, who sends transactional email after cutover so customers do not receive duplicates, and when the domain is expected to point at the new site. Active subscriptions in particular do not simply transfer between processors.

What would change the shape of this

Three answers above carry enough weight to change the size of the work rather than just its detail, and they are worth flagging separately:

  • Intake and accounts are unscoped today. If Bask hosts the questionnaire and its patient portal covers subscription management, both are small. If we are building either, each is a significant piece of design and build that is not in the current estimate.
  • Delayed capture is already promised in writing. The checkout tells customers their card is authorised now and charged on approval. If Bask cannot work that way, the copy is inaccurate and has to change before launch.
  • The domain already runs a live store. If there are existing customers or active subscriptions on it, this becomes a migration rather than a launch, with its own timeline and its own owner.

Summary

  • Bask manages the catalogue, pricing, plans, payments, orders, patients, prescriptions and pharmacy fulfilment. The site fetches all of it through the API and stores none of it.
  • Add to cart stays in the browser and is validated against live Bask pricing at checkout.
  • Checkout should be custom, driven by Bask's API with Bask hosted card fields, so the design survives and PCI scope stays with Bask.
  • Checkout is not the end of the purchase. Clinical review follows it, and the frontend has to represent that honestly.
  • The frontend is not made redundant by Bask. It carries the brand, the marketing site, the editable content, search visibility, the intake experience, consent and privacy control, and the entire cart and checkout experience.
  • The immediate blocker is Bask account and documentation access. Everything else follows from it, including the eight decisions above.
